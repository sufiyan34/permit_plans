Task lifecycle

  1. Task posted

    Client enters task title, description, category, budget range, deadline and attachments.

  2. Engineer submits a quote

    Engineer proposes an amount, estimated delivery time and message.

  3. Client accepts quote

    The selected quote becomes the agreed contract. Other quotes are closed.

  4. Client funds the task

    The payment provider confirms the payment and secures the funds under the agreed payment arrangement.

  5. Engineer starts working

    Task status becomes In Progress.

  6. Engineer submits deliverables

    Files, documentation, links and a completion message are submitted.

  7. Client reviews work

    Client can approve the delivery, request revisions or open a dispute.

  8. Payment released

    After approval, the payment provider sends the engineer's payout, less the platform commission.

I would also add automatic approval after a configurable review period, with a way to raise disputes before that deadline.

Requires early validation

This is where I want us to be particularly careful.

Your proposed payment system is:

The 10% is just an example; we can decide your actual commission later.

An important distinction: There is a difference between collecting a payment, temporarily delaying a merchant payout, and legally providing escrow.

For a Pakistan-first platform, the State Bank of Pakistan's EMI regulations allow domestic e-commerce escrow services by EMIs with separate SBP approval. SBP also states that ordinary PSOs/PSPs do not act as custodians of consumer money.

State Bank of Pakistan+1

That means we should not simply collect customer money into an ordinary company account and describe a Supabase balance as escrow.

Before implementing this feature, we need a payment partner that confirms it can support:

  1. Collecting client payments.

  2. Keeping transaction funds protected until an agreed release condition.

  3. Releasing funds to individual engineers.

  4. Refunding clients when appropriate.

  5. Pausing releases during disputes.

  6. Deducting platform commission.

  7. Providing verified payment and payout webhooks.

We should get written confirmation of the actual escrow arrangement and applicable regulatory permissions.

Card security: Never store the actual card number or CVV in Supabase. Let the payment provider handle card details and store only its payment-method token and permitted reference information.

Also, every payment must be verified through a secure server-side webhook. A success screen in Flutter must never be sufficient proof that money was received.

What happens technically?

A payment transaction could follow this state sequence:

CREATED → PENDING → FUNDED → RELEASE_PENDING → RELEASED

Other possible outcomes:

FAILED, REFUND_PENDING, REFUNDED, DISPUTED, PAYOUT_FAILED.

This will make payment tracking and admin reconciliation much more reliable.

4.3 Payment processing architecture

The Flutter application should never transfer money directly to an engineer.

The flow should be:

Flutter Client

Initiates checkout

Supabase Edge Function

Validates contract, creates payment session

Payment Provider

Collects and secures funds under its approved arrangement

Verified Webhook

Confirms payment status on the server

Supabase PostgreSQL

Records funded status and immutable ledger entries

Client approval

Requests authorized payout through the payment provider

We will use a payment adapter interface, something like:

dart
abstract class PaymentProvider {
  Future<CheckoutResult> createCheckout({
    required String contractId,
    required String currency,
    required int amountMinor,
  });

  Future<PayoutResult> releasePayout({
    required String paymentId,
  });

  Future<RefundResult> refund({
    required String paymentId,
    required int amountMinor,
  });

  Future<bool> verifyWebhook({
    required String payload,
    required Map<String, String> headers,
  });
}

The interface is our application's contract with a payment provider. The actual provider implementation will be kept on the server, not inside Flutter.

5.2 Important database design rules

Rule 1: One winning proposal per task.

When the client accepts a proposal, execute the operation transactionally. Only one engineer should be able to win a particular task, even if two requests arrive simultaneously.

Rule 2: Lock contract terms.

Once accepted, the proposal amount, currency, scope, deadline and included revisions must become the contract terms. Later changes require a recorded agreement.

Rule 3: Financial history is immutable.

We should use an append-only ledger rather than directly editing an engineer's balance.

Rule 4: Separate payments from payouts.

A successful client payment does not mean the engineer has received their money. These are separate records and events.

Rule 5: Idempotency.

The same webhook, release request or refund request must not create duplicate financial transactions.

Rule 6: No fake wallet balances.

Supabase can display earnings, pending payments and transaction histories. It must not independently hold customer money or represent an unregulated wallet.
